# Independent initial review: accessibility and scaling

Baseline: `593f879`, approved 0.2.0/build 8 implementation. This review used source and existing simulated tests only; it did not inspect another review or a proposed replacement design. No actual client rendering or assistive technology behavior is claimed. Severity: P1 = essential information can become inaccessible; P2 = material usability issue; P3 = polish or discoverability.

## Findings

| Priority | Concrete weakness and evidence | Player impact | Highest-value improvement |
| --- | --- | --- | --- |
| P1 | Essential current-stop information has fixed clipping limits. `UI.lua:73-74` gives the next instruction only 36 pixels; `UI.lua:213-215` caps the compact window at 360 and current text at 190, and expanded current text at 100. Member strings can append progress, unknown-return text and XP-estimate text (`30-46`), followed by destination, grouping, urgency, hints and notices (`188-210`). | A long quest name, multiple objectives or a missing-location notice can disappear without a way to scroll that current section. Expanded mode has a route scroll, but the player must discover the fallback and hunt for the missing message. | Measure wrapped current content; reserve explicit navigation/footer space; put bounded current detail into its own scrollable viewport when necessary. Never let long names displace the next action or navigation controls. |
| P2 | Almost all member/progress, status, route and help text uses `GameFontHighlightSmall` (`4-5`, `94`, `101`, `108-109`, `125-126`). The only larger text is the addon title; current instructions use `GameFontNormal` (`100`). There is no text or addon scale setting. | The branding has stronger legibility than the reason the tracker is open. Global UI scale adjustments can make this especially difficult for low-vision players. | Use a clear larger current-action font and normal-size body text. Offer a bounded saved addon scale setting or text-size choice; validate with existing saved positions and small available screen sizes. |
| P2 | Tracker dimensions are fixed at 500×640 expanded and 360 wide compact (`70`); feedback is fixed at 620×500 (`136`). Clamping only controls placement, not whether the whole frame fits. Feedback has no move handle. | At large game UI scales or small effective resolutions, bottom controls or report content can remain outside the visible area. Feedback may cover the important part of the scene and cannot be relocated. | Bound frame height/width to available UIParent space, make overflow scroll, and add a dedicated feedback drag handle. Preserve normalized tracker position when scale or mode changes. |
| P2 | Navigation status is fixed at 332×18 in both layouts (`108`), build/zone identity is 332×12 (`94`), and next action/controls use fixed widths. There is no explicit handling of long localized strings. | Longer zone names, translated controls, dependency failures or scaled fonts can clip exactly the state information needed to recover. | Wrap status at normal text size with measured height, separate build from zone text, and give buttons adequate width or explicit shortened labels with tooltips. Test synthetic long strings without publishing game text. |
| P2 | Header controls are terse `-`, `+` and `x` (`97-99`), with 28×24 targets. There are no tooltips or explicit text labels for their functions. The mode button cycles settings without indicating that it cycles (`110-112`). | Small motor targets and unfamiliar glyphs increase accidental hiding or layout changes; keyboard-only access is mainly indirect slash-command use. | Prefer named Compact/Expand/Hide controls or clear tooltips and generous targets. Document slash equivalents in contextual help; preserve native button behavior and avoid taking keyboard focus during normal tracking. |
| P2 | Feedback uses a one-line unlabeled note field (`144-147`), combines an empty marker and note save in one control (`148-151`), and places immediate `Clear feedback` alongside routine actions (`155-157`). Escape clears edit focus, but does not close the panel (`147`, `166`). | Players may not know where to type, whether a note was saved, or that clearing removes the local history. Mistakes are harder to recover from when reading or dexterity is reduced. | Add a visible note label, a saved/marked confirmation, distinct marker and note actions, and a confirmation or reversible clear flow. Provide clear close behavior that respects focused editing. |
| P3 | Route section and action headings use green/gold color (`219-226`) without other structural elements. Text labels already convey action meaning, so this is not exclusively color-dependent. However many member lines are plain indented strings with repeated coordinates and quest IDs (`227-231`). | Visual crowding and repetitive metadata make scanning tiring, especially when color perception is limited. | Retain explicit PICK UP/DO/TURN IN labels, add spacing and numbering/group counts, and move developer quest IDs out of the ordinary route view. Use color as reinforcement rather than the sole status signal. |
| P3 | The frame enables mouse input over its full rectangle (`83`), including mostly empty areas; expanded help and repeated status text add permanent clutter. | A large tracker can block interaction with the world even when locked, and its footprint is larger than its immediate information value. | Review which regions need mouse input, preserve reliable scrolling/buttons/dragging, and reduce persistent instructions to compact contextual help. Verify click-through behavior in client before promising it. |

## Contrast and evidence limits

The almost opaque dark background (`.035,.055,.065,.96`) provides a reasonable foundation, while native font objects determine the actual body text color and size. The green/gold heading values are explicit but actual contrast depends on the client font/template rendering, backdrop blending and effective scale. Do not claim a measured contrast ratio or accessibility compliance from these source values alone. A source-level improvement should use near-white body text, muted text that remains readable, and text labels for warnings and guidance state.

Existing tests (`tests/ui_test.lua`) simulate height as six pixels per byte and twelve pixels per line. They do not model WoW font metrics, UTF-8 glyph widths, actual clipping, effective UI scale, screen bounds smaller than a frame, mouse wheel behavior or visual contrast. They verify some saved position and toggle behavior, not these rendering risks.

## Priority verification matrix

1. Compact and expanded: one very long name, four grouped quests, multiple task/progress rows, long warning, timed hint and missing destination. Every essential message must remain reachable without overlap.
2. Effective UIParent sizes such as 800×600 and 1024×768 at normal and enlarged addon text/scale. Header and bottom controls must remain inside screen bounds.
3. Move, lock, switch layout, change scale, hide/show and simulated reload. Preserve a reachable saved position and preferences.
4. Missing TomTom, loading, unsupported zone, empty/completed plan. Meaning and recovery action must remain explicit without relying on color.
5. Feedback: type long Unicode text, save, mark, select/copy, cancel a clear, close/reopen, and ensure keyboard focus does not leak into ordinary gameplay.

## Recommended order

First remove current-content clipping and make navigation/empty-state recovery text reliably readable. Next establish normal-size body text and available-screen-aware layout. Then improve control labels and feedback safeguards, followed by spacing and secondary metadata cleanup. These changes should leave planner ordering, quest data, feedback persistence and owned-waypoint behavior intact.
